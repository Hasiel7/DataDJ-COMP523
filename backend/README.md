# Data DJ Backend

The backend is a Python 3.13 FastAPI application. It provides CSV dataset
validation and preparation, local dataset persistence, independent
library-backed dimensionality-reduction runners, and synchronous embedding
compute/retrieval endpoints.

## Setup

Run these commands from the repository root in PowerShell. `uv sync` reads the
Python version from `.python-version`, creates `backend/.venv`, resolves the
declared dependencies, and writes `uv.lock`.

```powershell
uv sync --project backend --dev
uv run --project backend uvicorn app.main:app --reload --app-dir backend
```

The API is available at `http://127.0.0.1:8000`; interactive API documentation
is at `http://127.0.0.1:8000/docs`.

## Verify

```powershell
uv run --project backend pytest -c backend/pyproject.toml
uv run --project backend ruff check .
```

## Dataset API

- `POST /api/datasets` accepts a multipart CSV file. Optional form fields are
	`label_column`, repeated `identifier_columns`, `row_id_column`,
	`preprocessing` (`none` or `standardize`), `max_samples` (1 through 100,000),
	`random_seed` (non-negative, default 42), and `has_header` (default true).
- `GET /api/datasets/{dataset_id}` returns dataset metadata.
- `GET /api/health` returns `{"status":"ok"}`.

## Dimensionality-Reduction Runners

The independent runners live in `app/dr/` and can be used without FastAPI:

```python
from app.dr.config import Algorithm, UMAPConfig
from app.dr.factory import run_reduction

coordinates = run_reduction(features, Algorithm.UMAP, UMAPConfig(), random_seed=42)
```

The factory accepts a two-dimensional, finite numeric NumPy matrix, an
`Algorithm` selection, its matching Pydantic config, and a non-negative seed.
It returns finite `float64` coordinates with shape `(n_samples, 2)`. A mismatched
algorithm/config pair or invalid matrix fails explicitly; an algorithm failure
is not hidden by substituting another method.

All methods accept `n_components=2` or `n_components=3` (default 2). The
supported configs are `UMAPConfig(n_neighbors, min_dist, n_epochs)`,
`TSNEConfig(perplexity, learning_rate, max_iter)`, and
`PHATEConfig(knn, t, decay)`. Configs reject additional settings. UMAP requires
`n_neighbors >= 2` and less than the sample
count, with `min_dist` in `[0, 1]` and positive `n_epochs`. t-SNE requires
`0 < perplexity < n_samples`, positive `learning_rate`, and `max_iter >= 250`
(the minimum supported by the installed scikit-learn API). PHATE requires
`1 <= knn < n_samples`, positive integer `t`, and non-negative `decay`.
Sample-count-dependent rules are checked by the runners immediately before the
library call.

The implementation uses `umap-learn`, `sklearn.manifold.TSNE`, and `phate`
directly. The current resolved APIs were checked with Python 3.13, including
scikit-learn's `max_iter` argument. The runner tests use small synthetic arrays;
they verify config validation, sample constraints, output shape, and finite
coordinates.

## Embedding API

- `POST /api/embeddings` accepts `dataset_id`, a discriminated `config` object,
	and optional non-negative `random_seed` (default 42). The config's
	`algorithm` selects `umap`, `tsne`, or `phate`, and `n_components` selects 2D
	or 3D output.
- `GET /api/embeddings/{embedding_id}` retrieves a result generated by this
	running API process.

POST returns `text/csv` with one observation per row. Columns are `row_id`,
optional `label`, and `embedding_1` through `embedding_2` or `embedding_3`.
`Content-Disposition` supplies a `.csv` filename; `X-Embedding-ID` provides the
result UUID. GET returns JSON metadata and coordinates. Before export, the
service checks stored features, labels, and row IDs are aligned; runners check
coordinate count and finiteness. Missing datasets/results return 404,
synchronous input-limit violations return 413, and invalid configs or algorithm
constraints return 422.

For initial synchronous computation, datasets are limited to 100,000
observations and 5,000 features per embedding request. There is no hard timeout:
reliable execution timeouts require isolated jobs or worker processes. Embedding
results are currently held in process memory, so they are lost on API restart
and are not shared across multiple server processes. CSVs are downloaded directly
and are not saved on the server; durable result persistence and caching are not
required for this workflow.

The separate reduction/export browser interface is served by Vite from
`main/reduction.html` at `http://localhost:8080/reduction.html`. It sends requests to
`http://127.0.0.1:8000/api` by default; set frontend environment variable
`VITE_API_BASE_URL` to override that base URL. The reduction page only prepares
datasets, computes embeddings, and downloads CSV; the existing visualization
page remains independent and loads that CSV for exploration.

Feature columns must contain numeric, non-missing, finite values. The label and
identifier columns are excluded from the feature matrix. If no row-ID column is
specified, zero-based source row positions are retained. Subsampling selects a
deterministic random subset without replacement, then restores source row order;
features, row IDs, and labels always use the same selected rows. Standardization
is fitted on the selected observations.

Set multipart field `has_header=false` for headerless numeric CSVs. The first
record is preserved as data, and columns are named `column_0`, `column_1`, and
so on. Select the appropriate generated column as the label when the file
contains labels (for a conventional MNIST CSV with label in column zero, select
`column_0`). The Reduction Lab has a “First row contains column names” checkbox
that controls both header inspection and upload parsing.

Prepared arrays and metadata are stored under `backend/data/datasets/{UUID}/`;
raw CSV files are not retained. Local datasets are kept until manually removed.
To clean up, stop the API and delete the corresponding UUID directory (or the
entire `backend/data/datasets/` directory to remove all local datasets). This
directory is git-ignored. Uploads are limited to 200 MiB and at most 100,000
observations may be selected. These synchronous safeguards do not provide a
hard execution timeout; reliable timeouts require isolated jobs or worker
processes.
