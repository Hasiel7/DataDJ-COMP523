# Data DJ Backend

The backend is a Python 3.13 FastAPI application. It provides CSV dataset
validation and preparation, local dataset persistence, independent
library-backed dimensionality-reduction runners, and synchronous embedding
compute/retrieval endpoints.

## Setup

Run these commands from the repository root in PowerShell. `uv sync` reads the
Python version from `.python-version`, creates `backend/.venv`, resolves the
declared dependencies, and writes `uv.lock`.

```powershell
uv sync --project backend --dev
uv run --project backend uvicorn app.main:app --reload --app-dir backend
```

The API is available at `http://127.0.0.1:8000`; interactive API documentation
is at `http://127.0.0.1:8000/docs`.

## Verify

```powershell
uv run --project backend pytest -c backend/pyproject.toml
uv run --project backend ruff check .
```

## Dataset API

- `POST /api/datasets` accepts a multipart CSV file. Optional form fields are
	`label_column`, repeated `identifier_columns`, `row_id_column`,
	`preprocessing` (`none` or `standardize`), `max_samples` (1 through 100,000),
	`random_seed` (non-negative, default 42), and `has_header` (default true).
- `GET /api/datasets/{dataset_id}` returns dataset metadata.
- `GET /api/health` returns `{"status":"ok"}`.

## Dimensionality-Reduction Runners

The independent runners live in `app/dr/` and can be used without FastAPI:

```python
from app.dr.config import Algorithm, UMAPConfig
from app.dr.factory import run_reduction

coordinates = run_reduction(features, Algorithm.UMAP, UMAPConfig(), random_seed=42)
```

The factory accepts a two-dimensional, finite numeric NumPy matrix, an
`Algorithm` selection, its matching Pydantic config, and a non-negative seed.
It returns finite `float64` coordinates with shape `(n_samples, 2)`. A mismatched
algorithm/config pair or invalid matrix fails explicitly; an algorithm failure
is not hidden by substituting another method.

All methods accept `n_components=2` or `n_components=3` (default 2). The
supported configs are `UMAPConfig(n_neighbors, min_dist, n_epochs)`,
`TSNEConfig(perplexity, learning_rate, max_iter)`, and
`PHATEConfig(knn, t, decay)`. Configs reject additional settings. UMAP requires
`n_neighbors >= 2` and less than the sample
count, with `min_dist` in `[0, 1]` and positive `n_epochs`. t-SNE requires
`0 < perplexity < n_samples`, positive `learning_rate`, and `max_iter >= 250`
(the minimum supported by the installed scikit-learn API). PHATE requires
`1 <= knn < n_samples`, positive integer `t`, and non-negative `decay`.
Sample-count-dependent rules are checked by the runners immediately before the
library call.

The implementation uses `umap-learn`, `sklearn.manifold.TSNE`, and `phate`
directly. The current resolved APIs were checked with Python 3.13, including
scikit-learn's `max_iter` argument. The runner tests use small synthetic arrays;
they verify config validation, sample constraints, output shape, and finite
coordinates.

## Embedding API

- `POST /api/embeddings` accepts `dataset_id`, a discriminated `config` object,
	and optional non-negative `random_seed` (default 42). The config's
	`algorithm` selects `umap`, `tsne`, or `phate`, and `n_components` selects 2D
	or 3D output.
- `GET /api/embeddings/{embedding_id}` retrieves a result generated by this
	running API process.

POST returns `text/csv` with one observation per row. Columns are `row_id`,
optional `label`, and `embedding_1` through `embedding_2` or `embedding_3`.
`Content-Disposition` supplies a `.csv` filename; `X-Embedding-ID` provides the
result UUID. GET returns JSON metadata and coordinates. Before export, the
service checks stored features, labels, and row IDs are aligned; runners check
coordinate count and finiteness. Missing datasets/results return 404,
synchronous input-limit violations return 413, and invalid configs or algorithm
constraints return 422.

For initial synchronous computation, datasets are limited to 100,000
observations and 5,000 features per embedding request. There is no hard timeout:
reliable execution timeouts require isolated jobs or worker processes. Embedding
results are currently held in process memory, so they are lost on API restart
and are not shared across multiple server processes. CSVs are downloaded directly
and are not saved on the server; durable result persistence and caching are not
required for this workflow.

The separate reduction/export browser interface is served by Vite from
`main/reduction.html` at `http://localhost:8080/reduction.html`. It sends requests to
`http://127.0.0.1:8000/api` by default; set frontend environment variable
`VITE_API_BASE_URL` to override that base URL. The reduction page only prepares
datasets, computes embeddings, and downloads CSV; the existing visualization
page remains independent and loads that CSV for exploration.

Feature columns must contain numeric, non-missing, finite values. The label and
identifier columns are excluded from the feature matrix. If no row-ID column is
specified, zero-based source row positions are retained. Subsampling selects a
deterministic random subset without replacement, then restores source row order;
features, row IDs, and labels always use the same selected rows. Standardization
is fitted on the selected observations.

Set multipart field `has_header=false` for headerless numeric CSVs. The first
record is preserved as data, and columns are named `column_0`, `column_1`, and
so on. Select the appropriate generated column as the label when the file
contains labels (for a conventional MNIST CSV with label in column zero, select
`column_0`). The Reduction Lab has a “First row contains column names” checkbox
that controls both header inspection and upload parsing.

Prepared arrays and metadata are stored under `backend/data/datasets/{UUID}/`;
raw CSV files are not retained. Local datasets are kept until manually removed.
To clean up, stop the API and delete the corresponding UUID directory (or the
entire `backend/data/datasets/` directory to remove all local datasets). This
directory is git-ignored. Uploads are limited to 200 MiB and at most 100,000
observations may be selected. These synchronous safeguards do not provide a
hard execution timeout; reliable timeouts require isolated jobs or worker
processes.
## Batch Jobs and Parallel Execution

`POST /api/jobs` validates and saves a grid as one queued batch job. Start the
automatic queue consumer from the repository root:

```powershell
uv run --directory backend python -m app.worker_cli --max-workers 3
```

It polls every two seconds while idle and processes one batch at a time, with
parallel configurations within that batch. `--once` drains available jobs and
exits instead of waiting for future submissions. A specific job can still be
executed by supplying its UUID:

```powershell
uv run --directory backend python -m app.worker_cli <job-id> --max-workers 3
```

To also deliver results to the current Windows user's Downloads folder and
send a desktop completion notification:

```powershell
uv run --directory backend python -m app.worker_cli <job-id> --max-workers 3 --download --notify
```

`--download-directory <path>` overrides the destination. This is a local file
copy on the worker computer, not a browser download. The original artifact
remains in place. Successful delivery creates `data-dj-{job-id}.zip` and a
matching `.completion.json` receipt with UTC start/end timestamps and elapsed
seconds from the database. Elapsed time covers job start through ZIP completion,
including interruptions on resumed jobs, but excludes queue waiting and the
subsequent Downloads copy. Notifications use Windows toasts and may be hidden by
Focus Assist or notification settings. Delivery and notification failures are
logged separately and do not change a successfully computed job to failed.

The CLI defaults to the smaller of 3 and the available CPU count. Use
`--max-workers 1` for serial execution or memory-constrained machines.
`BatchService(storage, max_workers=3)` enables the same behavior for Python
callers; its default remains serial. Single-run batches do not start a pool.

Parallel batches schedule individual configurations in round-robin algorithm
order, so a long grid for one method does not initially occupy every slot.
Joblib's `loky` backend runs them in separate processes, dispatches at most
the worker count initially, and limits supported numerical-library thread
pools to one thread per child. Large feature arrays use read-only memory maps
to reduce repeated serialization. Algorithm working memory still scales with
the number of concurrent runs.

All `JobExecutor` instances acquire an OS-backed lock beside the SQLite database
before claiming or resuming jobs. A continuous consumer holds it for its lifetime.
Another CLI invocation exits with code 2 instead of starting another pool.
The lock scope is one local database, even when callers use different artifact
directories. Separate databases, direct `BatchService` callers, and synchronous
embedding API requests are outside this budget. Never remove a lock file while
a worker is active; the file's presence alone does not mean it is locked.

Optional memory reservations reduce concurrency:

```powershell
uv run --directory backend python -m app.worker_cli --max-workers 3 --memory-budget-mb 4096 --memory-per-run-mb 1024
```

This reserves 1024 MiB for the coordinator and up to three runs. The derived
run count is `min(max_workers, floor(budget / reservation) - 1)`; insufficient
or incomplete reservations are rejected before accessing the database. These
are operator-provided estimates, not measured usage or OS-enforced RAM limits.
Choose reservations using measurements of representative datasets; algorithms
may allocate large pairwise matrices, and actual memory may exceed the estimate.

The coordinator checkpoints completed results under
`backend/data/artifacts/checkpoints/{job-id}/{identity-hash}/` by default.
`DATA_DJ_ARTIFACT_ROOT` overrides the artifact and checkpoint root; keep it
consistent between restarts. The identity includes the plan, seed, dataset
features and row identities, metadata, and library versions. Each result is
checksummed, flushed to disk, and atomically renamed from a temporary file.
Missing, malformed, mismatched, or corrupt results are recomputed. Changes to
inputs or library versions create a new checkpoint namespace, not mixed results.

After all runs succeed, the coordinator reads one result at a time in saved-plan
order to build the CSV and manifest. Only the coordinator writes exports; the
ZIP is published only after successful assembly. Completed checkpoints remain
after success or failure. Stop the worker before manually deleting checkpoints
that are no longer needed. There is no automatic retention policy yet.

On process crash or Ctrl+C, unfinished jobs remain `running`. Once a replacement
coordinator owns the lock, it considers interrupted running jobs before queued
jobs and computes only configurations without valid checkpoints. The OS releases
the lock on process exit; no heartbeat or timeout takeover is required. Recovery
is at configuration boundaries, not inside an interrupted algorithm. A caught
algorithm error marks the job `failed`, and the consumer continues to other jobs;
failed jobs are not automatically retried. Legacy jobs without saved plans are
skipped. Exit codes are 0 for success, 1 for failure, 2 for a busy coordinator or
unclaimable job, and 130 for Ctrl+C.

This is local, single-host recovery, not distributed scheduling. Force-killing a
coordinator may leave temporary files and briefly surviving library child
processes; inspect and stop orphaned workers before restarting if necessary.
Atomic checkpoints protect against interrupted writes, but sudden power loss
still depends on filesystem durability. A crash between ZIP publication and
recording job success may leave an unreferenced ZIP; a restart safely rebuilds
the package from checkpoints. No schema migration is required for these changes.

Grid axes already accept decimal strings for `start`, `stop`, and `step`:

```json
{
	"dataset_id": "<dataset-id>",
	"algorithms": {
		"tsne": {
			"perplexity": {"start": "1", "stop": "2", "step": "0.1"}
		}
	},
	"n_components": 2,
	"random_seed": 42
}
```

This produces 11 perplexity values, including both endpoints. Decimal arithmetic
avoids accumulated binary floating-point error when generating the range.
An endpoint is included only if the step reaches it exactly. Continuous
parameters are UMAP `min_dist`, t-SNE `perplexity` and `learning_rate`, and
PHATE `decay`. Neighbor counts, iteration counts, and PHATE `t` remain integers;
fractional values are rejected. Dataset-specific constraints still apply.

The limits are 200 total runs per job (combined across algorithms) and 1,000
values per axis. The saved execution plan uses the same 200-run cap. This is
a capacity limit, not a runtime guarantee, and does not change concurrency.
For initial timing tests, use 500-1,000 observations and 10-20 configurations
before attempting 200. Measure per-algorithm timings on the same dataset and
settings; increasing observation count can increase runtime nonlinearly.

## Viewing Large Batches

The explorer's **Open batch CSV** control accepts an exported batch directly;
researchers do not need a job ID. By default, the browser uploads the file with
transfer progress to `POST /api/batches/import`. FastAPI's multipart `UploadFile` spools
larger request bodies to a temporary file; the importer then parses that file
row by row rather than reading the complete upload into a bytes object. The
current upload limit is 2 GiB.
Multipart parsing receives the request before the route indexes it, so
large bodies are spooled to temporary disk (not retained in application RAM).
Deployments must set the reverse proxy/server request-body limit at least as
high as the application limit and provide temporary disk space for the incoming
file. The importer then makes compressed per-run partitions, so peak disk use
includes the upload spool plus partitions until request cleanup.

New generated CSVs include `run_number` on every row. The importer accepts both
that explicit format and older exports without it; legacy runs are inferred
from contiguous algorithm/configuration blocks. It validates configuration,
coordinates, unique observation IDs, row alignment across runs, sequential run
numbers, and size limits. It writes one gzip-compressed CSV partition at a time
under a staging directory. Only after the entire file validates does it
publish a catalog. With local storage it is placed under `DATA_DJ_BATCH_ROOT`
(default `backend/data/batches`); Blob storage uploads all partitions before
the catalog. Invalid uploads remove their local staging directory.

The returned opaque batch ID is a catalog reference, not a job ID. The UI loads
the small catalog and fetches `GET /api/batches/{batch_id}/runs/{run_number}`
for the selected run. It keeps at most the current run and its two neighbors in
a bounded browser cache, prefetching adjacent runs to make back/forward changes
fast without retaining the whole sweep. Upload indexing time depends on file
size, storage speed, and compression; switching to a cached adjacent run is
immediate, while a cache miss requires one run request.

PostgreSQL connections use a 5-second pool checkout timeout and a 10-second
libpq connection timeout. The application setting overrides `connect_timeout`
in `DATA_DJ_DATABASE_URL`. These limits do not bound every DNS lookup or
network stall on an established connection.

`DATA_DJ_DATASET_STORAGE=blob` stores imported batch partitions and catalogs
in the same private Blob container as datasets. By default, imports still happen
within the API request. The optional direct-upload workflow below moves the
upload to Blob Storage and indexing to the cloud worker. An interrupted import
can leave unreferenced Blobs that require a cleanup policy.
Large exhaustive sweeps still need progress reporting, explicit retry and
cancellation controls, compact previews, and retention limits before those
grid limits are raised. This worker adds local checkpoint recovery and automatic
queue consumption without changing the public job API.

### Direct batch uploads (private preview)

This feature is **off by default**. Before enabling it, back up the database,
review and apply the new Alembic migration, then deploy the updated API, frontend,
and cloud worker together. No migration or Azure configuration is applied
automatically. Set `DATA_DJ_DIRECT_BATCH_UPLOADS=1` on both the API and worker;
the API also requires PostgreSQL, `DATA_DJ_DATASET_STORAGE=blob`, and
`DATA_DJ_JOB_STORAGE=blob`. With the flag unset, the existing local and
synchronous workflows remain unchanged.

The API's managed identity must be able to obtain a user delegation key at
storage-account scope (the `Storage Blob Delegator` role provides that action)
and have the necessary Blob data permissions for the private `datadj` container.
The API needs permission to delete rejected sources; the worker needs Blob
read, write, and delete permissions for that container.
Review existing assignments and use the minimum suitable scopes; do not grant
account keys to the browser. See Microsoft's
[user delegation SAS guidance](https://learn.microsoft.com/azure/storage/blobs/storage-blob-user-delegation-sas-create-python).

Configure **Blob service CORS**, separately from API CORS, to allow the exact
Vercel origin and `PUT` with `content-type`, `x-ms-blob-type`, and
`x-ms-version` request headers. Add local development origins only if needed.
CORS is not authentication. The browser also needs network connectivity to the
Blob endpoint; a private container does not itself imply private networking.
If the storage firewall or private endpoint blocks the browser, direct upload
will fail. Do not make the container public.

1. After sign-in, `POST /api/batch-imports` requests a scoped, HTTPS-only,
   two-hour user-delegation SAS for one new source Blob. Treat the URL as a
   bearer secret; don't log, share, or persist it.
2. The browser sends the CSV to that Blob and calls
   `POST /api/batch-imports/{import_id}/complete`. The API checks the actual
   Blob length (nonempty, at most 2 GiB), saves its ETag, and queues the import.
3. The worker claims the import using a PostgreSQL lease and heartbeat, downloads
   the approved ETag to temporary disk, validates and indexes it, and uploads
   partitions followed by the catalog. A changed source fails rather than being
   indexed. The owner and completed batch ID are committed together only while
   the lease remains valid. An expired lease can be claimed by another worker.
4. The browser polls `GET /api/batch-imports/{import_id}` and opens the batch
   when it succeeds. Only its owner can complete or inspect an import. Failed
   imports currently require a new upload; there is no cancel, resume, or
   in-browser recovery after a page refresh.

The SAS does **not** enforce a byte limit during the upload. A holder can upload
an oversized Blob or rewrite the same Blob until the token expires; validation
occurs after upload and cannot prevent temporary storage charges. Quotas, rate
limits, and aggregate cost controls are not implemented. Successful and failed
worker imports attempt to delete the source, as do rejected oversized uploads;
deletion failures are logged. Abandoned uploads, recreated sources, and orphan
partitions can remain. Configure and verify a storage lifecycle policy for the
`batch-uploads/` prefix and plan separate cleanup for orphan batch partitions
and stale database records before relying on this feature. Account for the
source file **and** compressed partitions on worker temporary disk. A single
interrupted HTTP upload must be restarted, and a two-hour token can expire on
slow connections.

## Private cloud worker

The existing local `app.worker_cli` uses a filesystem lock and local artifacts.
Do not run it as the cloud worker. The separate cloud consumer uses PostgreSQL
leases, periodic heartbeats, and attempt-specific Blob checkpoints and exports:

```powershell
uv run --directory backend python -m app.cloud_worker_cli
```

Configure both API and worker with `DATA_DJ_DATABASE_URL` using
`postgresql+psycopg`, verified PostgreSQL TLS, and `DATA_DJ_BLOB_ACCOUNT_URL`.
The managed identity needs appropriate access to the private `datadj` container.
Set the API's `DATA_DJ_DATASET_STORAGE=blob` and `DATA_DJ_JOB_STORAGE=blob`;
the worker always uses PostgreSQL and Blob storage. Set a strong
`DATA_DJ_JWT_SECRET` on the API. Shared-storage startup fails if it is missing.
The same container image can run the worker with its command overridden to
`uv run --frozen --no-dev python -m app.cloud_worker_cli`. Initially run one
continuously available worker replica and size CPU, memory, and temporary disk
for the largest expected job.

The owner can retrieve a completed job's catalog, individual runs, or streamed
ZIP via `/api/jobs/{job_id}/batch`, `/api/jobs/{job_id}/runs/{run_number}`, and
`/api/jobs/{job_id}/export`. A completed job can also be opened from the
Reduction lab. ZIP export requires an authenticated HTTP client; the browser
does not yet offer a streaming download button. Synchronous embedding results
remain in process memory and are not shared across API replicas. Blob manifests
are published before ZIPs; a stale attempt cannot
publish its result, but can leave orphan Blobs. Cleanup and retention are not
implemented. Lease expiry prevents stale database publication, but does not
interrupt a scientific computation or bound every network stall.

Run migrations before starting the new code. Back up the Azure database and
confirm the deployment plan before running any migration against it; the code
changes do not automatically migrate or deploy Azure. Existing datasets, jobs,
and imported batches have no ownership record and are inaccessible through
authenticated endpoints until deliberately assigned to their verified owner.
The cloud worker skips unowned queued jobs.
Do not assign legacy data to an account without verifying ownership. Downgrading
the ownership migration discards ownership records.

Keep the API private until real Azure end-to-end testing, rate limits, quotas,
retention, backup/recovery, least-privilege access, and operational monitoring
are in place. Cleanup is incomplete, including orphaned worker artifacts.
No Azure resource or database migration is performed by these instructions.

## Accounts and Favorites

The visualizer's favorites are saved per user when signed in. The explorer only
shows Sign in and the Reduction lab link in development or when it is built with
`VITE_API_BASE_URL` set (locally, `http://127.0.0.1:8000/api`). Create or update
the database tables before starting the API (safe to run repeatedly):

```powershell
uv run --directory backend alembic upgrade head
```

- `POST /api/auth/register` and `POST /api/auth/login` take `{email, password}`
	(password at least 8 characters) and return `{access_token, user}`. A failed
	login always says "Invalid email or password".
- `GET /api/auth/me` returns the signed-in user. Send the token as
	`Authorization: Bearer <token>`; tokens last 7 days.
- `GET /api/favorites?file=<name>`, `POST /api/favorites`, and
	`DELETE /api/favorites/{id}` act only on the signed-in user's favorites.
- Dataset, embedding, grid, batch, and job endpoints require a bearer token.
  New resources are private to their creator; another user's resource and an
  unowned legacy resource both return 404. Local API use also requires sign-in.

Environment variables:

- `DATA_DJ_JWT_SECRET` signs the tokens. A development-only fallback is used
  only for local storage; shared PostgreSQL or Blob storage requires a secret.
- `DATA_DJ_CORS_ORIGINS` adds comma-separated browser origins, such as the
	GitHub Pages site (`https://<user>.github.io`), to the local Vite origins.
